# Lab 1 — Secure Engineer Onboarding with CloudFormation Git Sync

Repeatable, auditable IAM onboarding for Onward Logistics engineers, defined in
CloudFormation and deployed from Git. Every access change goes through a pull
request, every engineer is capped by a permissions boundary, and CloudTrail
records who changed access and when.

## Architecture

```
 GitHub repo (main)                AWS account
 ┌──────────────────────┐          ┌──────────────────────────────────────────┐
 │ deployment-file.yaml │  Git     │ CodeConnections ──► CloudFormation       │
 │ templates/           │  sync    │   connection          Git sync           │
 │   onboarding.yaml    │ ───────► │                        │ (onward-gitsync- │
 └──────────────────────┘          │                        │  role)           │
                                   │                        ▼                  │
                                   │              onboarding stack            │
                                   │              (onward-onboarding-stack-    │
                                   │               role)                      │
                                   │   ├─ permissions boundaries (3)          │
                                   │   ├─ IAM groups (3)                      │
                                   │   ├─ IAM users (3) + Secrets Manager     │
                                   │   └─ CloudTrail trail + audit S3 bucket  │
                                   └──────────────────────────────────────────┘
```

1. **Bootstrap (one time):** `bootstrap/gitsync-bootstrap.yaml` creates the Git
   connection and the two IAM roles that Git sync needs.
2. **Git sync (continuous):** CloudFormation watches this repository. When
   `deployment-file.yaml` or `templates/onboarding.yaml` changes on the tracked
   branch, it creates and runs a change set on the onboarding stack.

## Repository layout

| Path | Purpose |
| --- | --- |
| `bootstrap/gitsync-bootstrap.yaml` | One-time stack: CodeConnections connection, Git sync role, and the service role the onboarding stack deploys with. |
| `templates/onboarding.yaml` | The onboarding stack: boundaries, groups, users, initial passwords and the audit trail. |
| `deployment-file.yaml` | Git sync deployment file: the template path, stack parameters and stack tags. |
| `evidence.sh` | Script that produces evidence the controls work (policy simulation, stress test, CloudTrail lookup). |

## Access model

Effective permissions are the **intersection** of what a user's group grants and
what their permissions boundary allows. Attaching a broader policy to the user
or group later cannot take them past the boundary.

| User | Group (AWS managed policies) | Permissions boundary | Effective access |
| --- | --- | --- | --- |
| `s3-user` | `onward-<env>-storage-engineers`: `AmazonS3FullAccess` | `onward-<env>-boundary-storage`: `s3:*` | Full S3. No compute. |
| `ec2-user-1` | `onward-<env>-compute-engineers`: `AmazonEC2FullAccess` | `onward-<env>-boundary-compute`: EC2, ELB, Auto Scaling, CloudWatch read | Full compute. No S3. |
| `ec2-user-2` | `onward-<env>-oncall-observers`: `AmazonEC2ReadOnlyAccess` | `onward-<env>-boundary-compute-observer`: read-only, with explicit denies | Read-only compute. Cannot run, start or terminate instances, or change its own boundary. |

All three users also get `IAMUserChangePassword`, and every boundary lets the
user change only their own password.

Design rules the template follows:

- **No inline IAM policies.** Groups use AWS managed policies; boundaries are
  customer managed policies. The only inline document is the audit bucket
  policy, which CloudTrail requires.
- **No credentials in Git.** Initial passwords are generated by Secrets Manager
  and must be reset at first sign-in.
- **Audit by default.** A multi-region trail with global service events (where
  IAM events are recorded) and log file validation writes to an encrypted,
  versioned, private S3 bucket that is kept if the stack is deleted.

## Prerequisites

- An AWS account and admin credentials for the one-time bootstrap.
- AWS CLI v2, configured for that account.
- Admin access to the GitHub repository, to approve the connection.

## Deployment

### 1. Bootstrap the Git sync roles and connection

```bash
aws cloudformation deploy \
  --template-file bootstrap/gitsync-bootstrap.yaml \
  --stack-name onward-gitsync-bootstrap \
  --capabilities CAPABILITY_NAMED_IAM
```

The connection is created in the `PENDING` state. Complete the GitHub
handshake once in the console: **Developer Tools → Settings → Connections →
`onward-onboarding-repo` → Update pending connection**.

### 2. Create the onboarding stack with Git sync

In the CloudFormation console choose **Create stack → Sync from Git**, then set:

| Setting | Value |
| --- | --- |
| Stack name | e.g. `onward-onboarding-prod` |
| Connection | `onward-onboarding-repo` |
| Repository / branch | this repository, `main` |
| Deployment file path | `AWS/Lab1/deployment-file.yaml` |
| IAM role for Git sync | `onward-gitsync-role` |
| Stack service role | `onward-onboarding-stack-role` |

The bootstrap stack outputs (`ConnectionArn`, `GitSyncRoleArn`,
`StackDeployRoleArn`) give the exact values.

### 3. Make changes through pull requests

After the first sync, do not edit the stack from the console or CLI. Change
`templates/onboarding.yaml` or `deployment-file.yaml`, open a pull request,
and merge it to `main`. Git sync deploys the change.

## Onboarding an engineer

1. After a successful sync, read the stack outputs for the sign-in URL and the
   secret ARN for the new user.
2. Retrieve the first-login password:

   ```bash
   aws secretsmanager get-secret-value \
     --secret-id onward/prod/onboarding/s3-user \
     --query SecretString --output text
   ```

3. Send the username, password and `ConsoleSignInUrl` to the engineer through
   a secure channel. They must set a new password at first sign-in.

## Verifying the controls

`evidence.sh` produces evidence for a security review. Run it with admin
credentials against the deployed account:

```bash
ENV=prod bash evidence.sh
```

| Step | What it shows |
| --- | --- |
| 1. Day-one access | The IAM policy simulator confirms each user can do their job and nothing else. |
| 2. Stress test | Gives `ec2-user-2` and its group `AdministratorAccess`; the boundary still denies running, starting and terminating instances. |
| 3. Revert | Removes the `AdministratorAccess` policies again. |
| 4. Audit trail | CloudTrail shows who attached and detached the policies, and when. |
| 5. Boundaries | Each user has the boundary defined in Git. |

> **Warning:** step 2 grants `AdministratorAccess` to a real user for a short
> time. Run the script only in a lab account. If the script fails between
> steps 2 and 3, detach the policies by hand (see the commands in step 3).

CloudTrail event history can lag by several minutes. If step 4 returns empty
tables, run it again later.

## Configuration

Stack parameters are set in `deployment-file.yaml`:

| Parameter | Default | Description |
| --- | --- | --- |
| `Environment` | `prod` | Prefix for group, boundary, secret and trail names. Lowercase letters, digits and hyphens. |
| `CreateAuditTrail` | `true` | Set to `false` if the account already has an organization or account trail. |

Stack tags (`Project`, `Owner`, `ManagedBy`) are also set there and applied to
all supported resources.

## Known limitations

- **User names are fixed.** `s3-user`, `ec2-user-1` and `ec2-user-2` do not
  include `Environment`, so only one onboarding stack can exist per account.
- **The deploy role is broad.** `onward-onboarding-stack-role` has `iam:*`,
  `s3:*`, `secretsmanager:*` and `cloudtrail:*` on all resources. Scope it to
  the `onward-*` resource names before using this outside a lab.
- **`evidence.sh` does not clean up on failure.** See the warning above.

## Teardown

1. Delete the onboarding stack (in the console, disconnect Git sync first).
   The audit bucket is retained by design; empty and delete it by hand if
   the logs are no longer needed.
2. Delete the bootstrap stack:

   ```bash
   aws cloudformation delete-stack --stack-name onward-gitsync-bootstrap
   ```
